# Аудит безопасности

## Сводка

В ходе аудита Django-мессенджера Constanta обнаружено **18 уязвимостей и проблем безопасности**: 4 высокого (HIGH), 7 среднего (MEDIUM) и 7 низкого (LOW) уровня критичности. Наиболее критичные проблемы включают полный обход блокировки пользователей, XSS в middleware, и отсутствие rate limiting на аутентификацию.

---

## Найденные проблемы

### [HIGH] Обход блокировки пользователей (ban bypass)
- **Файл:** `users/backends.py:5-6`
- **Описание:** Метод `user_can_authenticate` в `CustomAuthBackend` всегда возвращает `True`. Это переопределяет стандартное поведение Django, при котором пользователи с `is_active=False` не могут аутентифицироваться. В проекте бан реализован через установку `is_active=False`, но данный backend полностью игнорирует этот флаг. Даже забаненный пользователь может войти в систему.
- **Рекомендация:** Удалить `CustomAuthBackend` или исправить `user_can_authenticate`, чтобы он возвращал `user.is_active`. Либо добавить проверку `is_active` в метод `authenticate`.

### [HIGH] XSS в IPBanMiddleware (отражённый)
- **Файл:** `users/middleware.py:24`
- **Описание:** IP-адрес пользователя напрямую интерполируется в HTML-ответ без экранирования. Заголовок `X-Forwarded-For` контролируется клиентом. Злоумышленник может отправить запрос с заголовком `X-Forwarded-For: <script>alert(document.cookie)</script>`, и скрипт выполнится в контексте сайта при попытке забаненного пользователя получить ответ.
- **Рекомендация:** Использовать `html.escape(ip)` или шаблон Django для рендеринга ответа вместо f-строки.

### [HIGH] DEBUG=True по умолчанию в production
- **Файл:** `Constanta/settings.py:10`
- **Описание:** Параметр `DEBUG` имеет значение по умолчанию `True`. Если переменная окружения `DEBUG` не установлена в production, Django будет показывать подробные страницы ошибок с трейсами стека, конфигурацией БД, секретными ключами и другой чувствительной информацией. Файл `.env.example` также содержит `DEBUG=True`, что способствует закреплению опасной практики.
- **Рекомендация:** Установить `DEBUG = env.bool('DEBUG', default=False)`. Удалить `DEBUG=True` из `.env.example`.

### [HIGH] Утечка SECRET_KEY через репозиторий
- **Файл:** `.env` (не отслеживается git, но файл существует на диске)
- **Описание:** Файл `.env` содержит секретный ключ Django: `django-insecure-^&d7q26w&+6!v%c05%p3n*d3q6e&_$5s#6r8$w=g&w*ijdqcbg`. Если этот файл или ключ когда-либо были зафиксированы в git (например, до добавления `.env` в `.gitignore`) — ключ скомпрометирован. Кроме того, ключ начинается с префикса `django-insecure-`, что является стандартным префиксом для автоматически сгенерированных ключей, но его наличие на диске — риск.
- **Рекомендация:** Немедленно сменить SECRET_KEY. Проверить историю git на наличие утечек. Использовать `python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"` для генерации нового ключа.

### [MEDIUM] Утечка внутренних ошибок через API
- **Файл:** `chat/views/api.py:87, 123, 151, 182, 209`
- **Описание:** Во всех исключениях API возвращает клиенту сырой текст ошибки через `str(e)`. Это может раскрыть внутреннюю структуру БД, имена таблиц, путей к файлам и другую техническую информацию, полезную для атакующего.
- **Рекомендация:** Возвращать общее сообщение об ошибке (например, "Внутренняя ошибка сервера"), а подробности логировать на сервере через `logging.exception()`.

### [MEDIUM] HTTP Header Injection в Content-Disposition
- **Файл:** `chat/views/api.py:232`
- **Описание:** Оригинальное имя файла (`attachment_original_name`) используется в заголовке `Content-Disposition` без санитизации. Если имя файла содержит символы CRLF (`\r\n`), злоумышленник может внедрить произвольные HTTP-заголовки в ответ.
- **Рекомендация:** Экранировать имя файла: заменить CR/LF символы, или использовать `urllib.parse.quote()`, или использовать `Content-Disposition: attachment; filename*=UTF-8''<encoded_name>`.

### [MEDIUM] Отсутствие валидации типа файлов при загрузке (MIME-spoofing)
- **Файл:** `chat/views/api.py:42-51`
- **Описание:** Тип вложения (`image`, `voice`, `file`) определяется исключительно по заголовку `Content-Type`, который контролируется клиентом. Злоумышленник может загрузить .exe файл с заголовком `Content-Type: image/png`, и он будет отображаться как изображение. Дополнительно: в `group_chat.html:370` и `index.html:225` изображения рендерятся через `<img src="{{ msg.attachment.url }}">`, что может привести к загрузке вредоносного файла браузером с неверной MIME-меткой.
- **Рекомендация:** Проверять magic-байты файла (через `python-magic` или стандартную сигнатуру). Для изображений использовать Pillow для проверки, является ли файл валидным изображением. Не полагаться только на `content_type`.

### [MEDIUM] Отсутствие rate limiting на аутентификацию
- **Файл:** `users/views/auth.py:10-49`
- **Описание:** Эндпоинт `/auth/` не имеет ограничения на количество попыток входа. Это позволяет проводить атаки brute-force на пароли пользователей. Нет блокировки после N неудачных попыток, нет CAPTCHA, нет задержки между попытками.
- **Рекомендация:** Добавить rate limiting через `django-ratelimit` или `django-throttle-requests`. Ограничить до 5-10 попыток в минуту с одного IP.

### [MEDIUM] Отсутствие secure cookie флагов
- **Файл:** `Constanta/settings.py`
- **Описание:** В production-окружении не настроены следующие важные параметры безопасности: `SESSION_COOKIE_SECURE` (куки сессии не помечены как Secure), `CSRF_COOKIE_SECURE` (CSRF-куки не помечены как Secure), `SECURE_SSL_REDIRECT` (нет принудительного HTTPS), `SECURE_HSTS_SECONDS` (нет HSTS), `SECURE_CONTENT_TYPE_NOSNIFF`. В отсутствие HTTPS и HSTS возможны атаки перехвата сессии (session hijacking).
- **Рекомендация:** Добавить в settings.py: `SESSION_COOKIE_SECURE = True`, `CSRF_COOKIE_SECURE = True`, `SECURE_SSL_REDIRECT = True`, `SECURE_HSTS_SECONDS = 31536000`, `SECURE_HSTS_INCLUDE_SUBDOMAINS = True`, `SECURE_CONTENT_TYPE_NOSNIFF = True`.

### [MEDIUM] Небезопасное получение CSRF-токена из cookie в JavaScript
- **Файл:** `templates/base.html:68-71`
- **Описание:** JavaScript-код считывает CSRF-токен напрямую из cookie: `document.cookie.match(/csrftoken=([^;]+)/)`. Рекомендуемый подход — брать токен из DOM: `document.querySelector('[name=csrfmiddlewaretoken]').value`. Хотя текущая реализация работает, она делает токен уязвимым при включении `CSRF_COOKIE_HTTPONLY = True`. Кроме того, в случае XSS на поддомене, атакующий может прочитать CSRF-куки.
- **Рекомендация:** Использовать токен из DOM-элемента формы, а не из cookie. Пример: `document.querySelector('[name=csrfmiddlewaretoken]').value`.

### [MEDIUM] Потенциальный XSS через parse_mentions (неактивен, но опасен)
- **Файл:** `chat/utils.py:109-112, 124-139`
- **Описание:** Функция `parse_mentions` вставляет в контент неэкранированные HTML-теги (спаны и ссылки) через f-строки и `re.sub.username` вставляется напрямую в href и innerHTML. Функция `format_mention_content` пытается "безопасно" восстановить HTML, используя хрупкие регулярные выражения, которые могут быть обойдены. Хотя в текущих шаблонах `|safe` не используется (экранирование Django защищает), при любом будущем использовании `|safe` или `mark_safe` эта функция станет вектором XSS.
- **Рекомендация:** Использовать `format_html()` Django для безопасного построения HTML. Избегать ручного конструирования HTML через конкатенацию строк. Добавить санитизацию через `bleach` или `html_sanitizer`.

### [LOW] Неравномерная проверка прав в add_member
- **Файл:** `chat/views/group.py:84` vs `chat/views/api.py:139`
- **Описание:** В `chat/views/group.py:84` добавлять участников могут `owner` или `admin`. В `chat/views/api.py:139` — только `owner`. Это создаёт непоследовательность: через веб-интерфейс админ может добавить участника (GET/POST форма), через API — нет (только владелец). Сама по себе уязвимость не критична, так как admin — доверенная роль, но создаёт путаницу.
- **Рекомендация:** Привести оба эндпоинта к единой логике авторизации.

### [LOW] Длинный срок жизни сессии
- **Файл:** `Constanta/settings.py:142`
- **Описание:** `SESSION_COOKIE_AGE = env.int('SESSION_COOKIE_AGE', default=1209600)` — 14 дней. Долгая сессия увеличивает окно атаки при угоне cookie.
- **Рекомендация:** Уменьшить значение до 86400 (1 день) или 43200 (12 часов) для мессенджера.

### [LOW] Отсутствие CSP-заголовков
- **Файл:** `Constanta/settings.py` (не настроено)
- **Описание:** Не настроена Content Security Policy. Это позволяет выполнение инлайн-скриптов и скриптов с любых внешних источников (CDN). На страницах используются инлайн-скрипты, что делает защиту через CSP особенно важной.
- **Рекомендация:** Добавить `Content-Security-Policy` через middleware или на уровне веб-сервера. Как минимум: `default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; style-src 'self' https://cdn.jsdelivr.net`.

### [LOW] Hardcoded IP-адреса в ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS
- **Файл:** `Constanta/settings.py:12-18`
- **Описание:** В `ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS` жестко прописаны IP-адреса: `1.1.1.71`, `192.168.1.67`. Они не являются приватными/локальными (кроме `127.0.0.1` и `192.168.1.67`). Если эти адреса — реальные IP сервера, они раскрывают информацию об инфраструктуре.
- **Рекомендация:** Вынести в переменные окружения без значений по умолчанию (кроме `localhost` и `127.0.0.1` для разработки).

### [LOW] Отсутствие валидации email при изменении профиля
- **Файл:** `users/views/profile.py:23-24`
- **Описание:** Email устанавливается напрямую из POST-данных без какой-либо валидации: `user.email = new_email`. Можно установить невалидный email (например, `notanemail`). Django-модель User не имеет встроенной валидации email-адреса (это просто CharField).
- **Рекомендация:** Использовать `EmailField` или форму с `EmailValidator`. Как минимум: `from django.core.validators import validate_email; validate_email(new_email)`.

### [LOW] Отсутствие проверки лимитов при создании группы
- **Файл:** `chat/views/group.py:50-58`
- **Описание:** В `settings.py:147` определён `MAX_GROUPS_PER_USER = 50`, но он нигде не проверяется. Пользователь может создать неограниченное количество групп.
- **Рекомендация:** Добавить проверку перед созданием группы: `if Group.objects.filter(owner=request.user).count() >= settings.MAX_GROUPS_PER_USER: messages.error(...); return redirect(...)`.

### [LOW] API эндпоинты со старыми названиями URL
- **Файл:** `chat/views/api.py:17` (заглушки на импорт)
- **Описание:** В `api.py:14-17` используется try/except для импорта `parse_mentions` и `create_notification`, с определением функций-заглушек при ошибке. Это маскирует реальные проблемы импорта и может скрыть баги. Сами функции импортируются, но нигде не вызываются в `send_message`.
- **Рекомендация:** Удалить неиспользуемые импорты. Если функционал упоминаний не реализован — удалить связанный код. Если планируется — реализовать и вызывать.

## Рекомендации общего характера

1. **Использовать HTTPS** — настроить反向代理 (nginx/Caddy) с Let's Encrypt, включить принудительный редирект на HTTPS и HSTS.
2. **Установить `django-cors-headers`** — если планируются кросс-доменные запросы, настроить CORS явно, а не через `CSRF_TRUSTED_ORIGINS`.
3. **Настроить rate limiting** — обязательно для `/auth/`, желательно для API-эндпоинтов (отправка сообщений, создание групп).
4. **Добавить Content Security Policy (CSP)** — для предотвращения XSS и снижения ущерба при его возникновении.
5. **Регулярно обновлять зависимости** — проверить версию Django на наличие известных CVE.
6. **Добавить `SecurityMiddleware` настройки** — явно задать все параметры вместо использования умолчаний: `SECURE_REFERRER_POLICY`, `SECURE_PROXY_SSL_HEADER`, `X_FRAME_OPTIONS`.
7. **Использовать формы Django** — для профиля и групп вместо ручного извлечения `request.POST`, чтобы использовать встроенную валидацию и очистку.
8. **Пересмотреть модель бана** — вместо флага `is_active` использовать отдельное поле `is_banned`, чтобы не нарушать стандартную логику аутентификации Django.
9. **Мониторинг и аудит** — добавить алерты на необычную активность (много неудачных логинов, подозрительные загрузки файлов).
10. **Проверить `.gitignore`** — убедиться, что `.env` и другие файлы с секретами исключены из репозитория. Очистить историю git, если были утечки.
