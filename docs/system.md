# Аудит бэкенда

## Сводка

Всего найдено **27 проблем**: **3 HIGH**, **11 MEDIUM**, **13 LOW**. Критические ошибки связаны с потерей данных при регистрации, неработающими упоминаниями/уведомлениями и игнорированием конфигурации.

---

## Найденные проблемы

### [HIGH] Поле `nick` не сохраняется при регистрации
- **Файл:** `users/forms.py:6-11`
- **Описание:** `RegistrationForm` объявляет поле `nick`, но оно отсутствует в `Meta.fields` (только `username`, `password1`, `password2`). `ModelForm.save()` заполняет только поля из `Meta.fields`, поэтому значение `nick` теряется при создании пользователя. Пользователь регистрируется с ником, но он не сохраняется в БД.
- **Рекомендация:** Добавить `nick` в `Meta.fields` или переопределить `save()` в форме.

### [HIGH] `parse_mentions` и `create_notification` импортированы, но не вызываются
- **Файл:** `chat/views/api.py:13-17, 62-78`
- **Описание:** В `send_message()` импортированы `parse_mentions` и `create_notification`, но ни одна из функций не вызывается при создании сообщения. Поле `Message.mentions` никогда не заполняется, уведомления для упомянутых пользователей не создаются. Функциональность упоминаний и уведомлений полностью не работает.
- **Рекомендация:** Вызвать `parse_mentions(content, group=group)` перед сохранением сообщения, сохранить результат в `msg.mentions`, и вызвать `create_notification` для каждого упомянутого пользователя.

### [HIGH] Жёстко заданный лимит символов вместо настройки из settings
- **Файл:** `chat/views/api.py:33-35`
- **Описание:** `MAX_CHARS = 500` задан константой, а в `settings.py:148` определён `MAX_MESSAGE_LENGTH = env.int('MAX_MESSAGE_LENGTH', default=2000)`. Настройка из settings не используется. Пользователи не могут отправлять сообщения длиннее 500 символов, хотя конфигурация разрешает 2000.
- **Рекомендация:** Использовать `from django.conf import settings` и `settings.MAX_MESSAGE_LENGTH` вместо хардкода.

### [MEDIUM] N+1 запрос при разборе @упоминаний
- **Файл:** `chat/utils.py:100-105`
- **Описание:** В `parse_mentions()` для каждого `@username` выполняется отдельный запрос `User.objects.get(username=username)` внутри цикла. При 10 упоминаниях — 10 запросов к БД.
- **Рекомендация:** Заменить на один запрос `User.objects.filter(username__in=matches)` и построить словарь `{username: user}`.

### [MEDIUM] N+1 запросы в админке — member_count и message_count
- **Файл:** `chat/admin.py:54-61`
- **Описание:** Методы `member_count()` и `message_count()` в `UltimateGroupAdmin` выполняют отдельные `COUNT`-запросы для каждой группы в списке. При 50 группах — 100 лишних запросов.
- **Рекомендация:** Использовать `get_queryset().annotate(member_count=Count('members'), message_count=Count('messages'))` и обращаться к аннотированным полям.

### [MEDIUM] Нет пагинации в каталоге пользователей
- **Файл:** `users/views/profile.py:44-53`
- **Описание:** `users_catalog()` загружает **всех** пользователей, кроме текущего, без пагинации. При 10 000 пользователях — massive queryset.
- **Рекомендация:** Добавить `from django.core.paginator import Paginator` и пагинировать результат (например, по 50 на страницу).

### [MEDIUM] Нет пагинации в списке чатов и сообщениях
- **Файл:** `chat/views/chat.py:17-42`
- **Описание:** `messages_list` (строка 39-42) и `chat_users` (строка 22-26) не имеют пагинации или ограничения. Если у пользователя тысячи друзей или сообщений — всё загружается в память.
- **Рекомендация:** Добавить лимит (`.order_by('-created_at')[:100]`) или пагинацию для списка сообщений и чатов.

### [MEDIUM] Голый `except Exception` в API-вьюхах
- **Файл:** `chat/views/api.py:86, 122, 150, 181, 208`
- **Описание:** Во всех API-эндпоинтах используется `except Exception as e:`, что перехватывает все исключения, включая `KeyboardInterrupt` и `SystemExit`. В production это может маскировать критические ошибки.
- **Рекомендация:** Использовать конкретные типы исключений (`ObjectDoesNotExist`, `ValidationError`), или хотя бы `except Exception` с логированием и `raise` для критичных.

### [MEDIUM] Несоответствие прав доступа между view и API
- **Файл:** `chat/views/group.py:84` vs `chat/views/api.py:139`
- **Описание:** `add_member` в `group.py` разрешает добавление админам (`membership.role in ['owner', 'admin']`), а `api_add_member` — только владельцу (`group.owner != request.user`). Аналогично для `remove_member`. Несоответствие запутывает и может блокировать легитимные действия админов через API.
- **Рекомендация:** Привести проверки к единому стандарту — либо везде owner+admin, либо везде только owner.

### [MEDIUM] `bio` не обрабатывается в profile_view; ProfileForm не используется
- **Файл:** `users/views/profile.py:11-37`
- **Описание:** В `profile_view()` поле `bio` не читается из `request.POST`, хотя форма `ProfileForm` (в `users/forms.py:18-26`) содержит `bio`. Форма объявлена, но нигде не используется — профиль редактируется вручную через `request.POST`.
- **Рекомендация:** Либо использовать `ProfileForm` в `profile_view`, либо добавить обработку `bio` вручную.

### [MEDIUM] Дублирование раздачи медиа в DEBUG-режиме
- **Файл:** `Constanta/urls.py:14-15` и `chat/urls.py:27-28`
- **Описание:** Оба URL-конфига добавляют `static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)` в `urlpatterns` при `DEBUG=True`. Это приводит к дублированию URL-паттернов и потенциальным конфликтам.
- **Рекомендация:** Оставить раздачу медиа только в `Constanta/urls.py`, убрать из `chat/urls.py`.

### [MEDIUM] `change_role` не проверяет, что цель — не сам владелец
- **Файл:** `chat/views/group.py:119-129`
- **Описание:** Функция `change_role()` не проверяет, пытается ли владелец изменить свою собственную роль. Владелец может установить себе роль `member`, фактически лишив себя прав (хотя поле `Group.owner` останется).
- **Рекомендация:** Добавить проверку `if target.user == group.owner: messages.error(...); return redirect(...)`.

### [MEDIUM] `api_set_role` через `get_or_create` создаёт членство не-участникам
- **Файл:** `chat/views/api.py:175`
- **Описание:** `GroupMember.objects.get_or_create(group=group, user=target_user)` добавляет пользователя в группу, если его там нет. Владелец может добавить любого пользователя, просто назначив ему роль через API, минуя обычный флоу добавления.
- **Рекомендация:** Использовать `GroupMember.objects.get(group=group, user=target_user)` и возвращать ошибку, если пользователь не в группе.

### [LOW] Неполный `__all__` в `chat/views/__init__.py`
- **Файл:** `chat/views/__init__.py:8-13`
- **Описание:** Из `api.py` импортируются `download_attachment`, `api_set_role`, `api_remove_member`, `api_add_member`, `api_update_group`, но они отсутствуют в `__all__`. `from chat.views import *` не экспортирует эти имена.
- **Рекомендация:** Добавить недостающие имена в `__all__`.

### [LOW] Мёртвый код: `LoginForm` не используется
- **Файл:** `users/forms.py:14-15`
- **Описание:** Класс `LoginForm(AuthenticationForm)` определён, но в `auth_view` используется стандартный `AuthenticationForm` напрямую. `LoginForm` — мёртвый код.
- **Рекомендация:** Удалить или использовать в `auth_view`.

### [LOW] Неинформативная ошибка при неверном логине
- **Файл:** `users/views/auth.py:39`
- **Описание:** При невалидной форме входа показывается общее сообщение `❌ Проверьте правильность ввода` вместо конкретных ошибок формы (неверный пароль, пользователь не найден и т.д.).
- **Рекомендация:** Выводить ошибки формы аналогично блоку регистрации (строки 22-24).

### [LOW] Неверный HTTP-статус в `api_heartbeat` для не-POST
- **Файл:** `chat/views/api.py:246`
- **Описание:** При GET-запросе к `/api/heartbeat/` возвращается `400 Bad Request`. Корректный статус — `405 Method Not Allowed`.
- **Рекомендация:** Использовать `status=405` вместо `status=400`.

### [LOW] `reply_to` не проверяется на контекст чата
- **Файл:** `chat/views/api.py:55-56`
- **Описание:** При указании `reply_to_id` не проверяется, что указанное сообщение принадлежит тому же диалогу/группе. Можно ответить на сообщение из другого чата, что приведёт к некорректному отображению.
- **Рекомендация:** Проверять, что `reply_msg.group == group` (для группы) или `reply_msg` принадлежит тем же участникам (для лички).

### [LOW] Импорты внутри функции `main_chat`
- **Файл:** `chat/views/chat.py:15`
- **Описание:** `from django.db.models import OuterRef, Subquery` импортируется внутри тела функции, а не в начале файла. При каждом вызове `main_chat` выполняется повторный импорт.
- **Рекомендация:** Перенести импорты в начало файла.

### [LOW] `export_group_members` — N+1 запрос в админ-экшене
- **Файл:** `chat/admin.py:78-80`
- **Описание:** Для каждой выбранной группы выполняется отдельный запрос `GroupMember.objects.filter(group=group)`. При 20 группах — 20 лишних запросов.
- **Рекомендация:** Собрать все `group_id` и сделать один запрос `GroupMember.objects.filter(group_id__in=group_ids).select_related('user')`.

### [LOW] Несоответствие лимита сообщений: группа 50, личка — без лимита
- **Файл:** `chat/views/group.py:38` vs `chat/views/chat.py:39-42`
- **Описание:** В групповом чате сообщения ограничены 50 (`[:50]`), в приватном — без ограничений. Непоследовательное поведение.
- **Рекомендация:** Установить одинаковый лимит (или добавить пагинацию в оба места).

### [LOW] `_file_hash` читает весь файл в память
- **Файл:** `chat/models.py:10-14`
- **Описание:** Функция `_file_hash()` вызывает `file_obj.read()`, что загружает весь файл в память для хеширования. Для файлов размером 10MB это избыточно.
- **Рекомендация:** Использовать построчное/поблочное чтение через `hashlib.sha256()` с `file_obj.read(block_size)` в цикле.

### [LOW] Имя файла в Content-Disposition без кодировки
- **Файл:** `chat/views/api.py:232`
- **Описание:** `original_name` подставляется напрямую в заголовок `Content-Disposition`. Если имя содержит не-ASCII символы (русские, китайские), оно будет некорректно обработано браузером.
- **Рекомендация:** Использовать `from wsgiref.util import FileWrapper` и `from django.utils.text import slugify`, или кодировать через `rfc6266`.

### [LOW] Групповые сообщения без выбора участников не имеют receiver/group
- **Файл:** `chat/views/api.py:60-82`
- **Описание:** Если не указан ни `friend_id`, ни `group_id`, возвращается `'Нет получателя'`. Но проверка `if not content and not attachment` выполняется раньше, так что пустое сообщение без получателя вернёт неверную ошибку.
- **Рекомендация:** Проверять наличие `friend_id` или `group_id` до проверки контента, чтобы возвращать корректное сообщение об ошибке.

### [LOW] `api_update_group` — не обрабатывает случай удаления аватарки
- **Файл:** `chat/views/api.py:113-116`
- **Описание:** Если в запросе нет поля `avatar`, старая аватарка остаётся. Нет возможности удалить аватарку (только заменить). Нет поля `remove_avatar` или подобного.
- **Рекомендация:** Добавить обработку параметра `remove_avatar` для удаления аватарки.

### [LOW] Рассылка уведомлений не использует `transaction.on_commit`
- **Файл:** `chat/utils.py:144-153`
- **Описание:** `create_notification` создаёт запись в БД сразу, но сообщение может быть не закоммичено (например, при ошибке на следующей строке). При откате транзакции уведомление останется сиротой.
- **Рекомендация:** Использовать `from django.db import transaction` и `transaction.on_commit(lambda: Notification.objects.create(...))`.

## Общие рекомендации

1. **Пересмотреть обработку упоминаний** — функциональность задумана, но полностью не работает. Необходимо интегрировать `parse_mentions` в `send_message()` в `api.py`.
2. **Устранить N+1 запросы** — особенно в `parse_mentions`, админ-панели и списках друзей.
3. **Добавить пагинацию** во все списки (пользователи, сообщения, чаты) — фундаментально для масштабирования.
4. **Унифицировать проверки прав** — API и view-функции для групп должны использовать одинаковую логику.
5. **Убрать дублирование** раздачи медиа между `Constanta/urls.py` и `chat/urls.py`.
6. **Заменить голые `except Exception`** на конкретные типы исключений с обязательным логированием.
7. **Синхронизировать конфигурацию** — использовать `settings.MAX_MESSAGE_LENGTH` вместо хардкода.
8. **Добавить тесты** для критических путей: регистрация (сохранение nick), отправка сообщений (упоминания, уведомления), работа с группами.
